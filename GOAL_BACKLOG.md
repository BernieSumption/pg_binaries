## Publication readiness

- [ ] Implement and test candidate inventory and publication logic without creating a GitHub Release. Local candidate generation and preflight have CLI entry points and tests for retained URLs, staged bytes, and explicit redistribution declarations. Candidate drafts retain proposed verification records by new URL; preflight requires passed current-profile publication records for both OS endpoints, every SQL name and PostgreSQL range endpoint, matching staged bytes and the exact assembled core archive. This validates the records' applicability without independently establishing that the recorded tests ran. The candidate generator requires archive names to identify the declared component, version, platform and PostgreSQL build target or range. Candidate generation and coverage also compare the assembled core checksum with the claimed core download, including retained core URLs. A project-level proposal fans one archive URL and its SQL-name-specific endpoint evidence out to every SQL extension name declared for that project; preflight accepts that shared URL and checks the required sibling extension metadata against support. A filesystem dry run tests ordering, retained references, checksums, and failures before the current inventory changes. GitHub upload checks and anonymous retrieval still require a publication-capable integration test. The eventual publication flow must place verified assets before a new inventory becomes public.
- [ ] Define a publication verification profile before emitting any publication-scoped record. Linux x86-64 PostgreSQL 18.6 with pgvector 0.8.7 is the smallest practical first slice because both OS endpoints already run the same verifier. The shared pgvector test now asserts the HNSW access method, and the Linux verifier checks representative restored catalogue definitions; a local Docker run passed against PostgreSQL 18.6 archive bytes on 2026-10-17. Before publication evidence, establish the exact current verifier image and dependency-closure proof, candidate inventory-to-archive reconciliation, and a CI emitter for fail-closed case results. Record validation now requires one consistent outcome for every named publication case. Keep diagnostics in the current-OS profile; the Linux 5.15 guest does not run that case. Then run new publication checks against exact final bytes; historical pilot records cannot be relabeled. A complete intended-support matrix and post-publication anonymous retrieval remain separate requirements.
- [ ] Reassess the release restriction after each substantial milestone. Stop this goal when enabling releases becomes the appropriate next step, with a concrete proposed release action, evidence, remaining gaps, and the checks that require actual publication.
