# Build and testing architecture review, 18 October 2026

This review covers the selected PostgreSQL 15–18 releases on five declared OS/architecture targets and uses pgvector, pgTAP and HypoPG to test the extension workflow. It evaluates the tooling needed to expand support; it does not authorize publication or claim that every selected archive exists. The public `inventory.json` is absent. The support selector currently derives 20 PostgreSQL targets and 60 archive targets for these three extensions; the full selected extension set has 303 SQL extension targets.

## Where verification runs

Build jobs produce core or extension archives. Verification must consume the final archive bytes and assemble an installation using the documented copy procedure. A verification record binds its result to the archive SHA-256, selected PostgreSQL archive, profile revision, target and runner environment. Static dependency inspection and relocated PostgreSQL/SQL behavior are separate required cases. A passing build or local smoke test alone cannot satisfy a publication profile.

- Linux builds run inside Docker. The final archives are assembled, moved and exercised in a separate Alpine verifier container on the runner, including ELF dependency inspection. The container isolates the test from the Ubuntu userspace; it shares the runner kernel. Existing Linux publication runs have imported archive-bound records for the reference components on both architectures and selected PostgreSQL releases, but the current public inventory has no downloads to reconcile against them.
- The macOS PostgreSQL/pgvector pilot and Windows PostgreSQL/pgvector pilot have separate build and verification runner jobs. Their verifier downloads the archives, performs native dependency inspection and exercises the relocated installation. The HypoPG macOS arm64/PostgreSQL 17.11 workflow now has a separate fresh-runner verification job. [Run 39135932527](hypopg-macos-publication-39135932527/README.md) passed both the archive suite and static analysis; its retained record binds the extension to the exact PostgreSQL archive. The corresponding Windows HypoPG PG17.11 workflow also passed [fresh-runner verification](hypopg-windows-publication-39137163791/README.md), including relocation, SQL behavior and 142 PE inspections.
- The other reviewed macOS and Windows pgTAP/HypoPG extension publication workflows still build and verify on the same runner. Their retained records identify final archive hashes, but the runner arrangement does not meet `policies/testing.md`'s fresh-runner requirement. Those results remain useful diagnostic evidence, not proof that this requirement is met. The same audit should be applied before treating other extension workflows as compliant.

The verifier environment still contains GitHub runner tools. Native dependency inspection restricts allowed imports and search paths, while relocation and behavior checks catch dependencies selected at runtime. The project does not claim that a passing runner test proves independence from every installed tool or file. Routine minimum-OS execution is not required by the testing specification; deliberate build settings and binary evidence address the declared floor.

## Planning, reuse and dispatch

`support.json` and the PostgreSQL release snapshot drive exact selected targets. `tools/extension_archive_plan.py` groups one project release, platform and PostgreSQL major into an archive candidate. `tools/extension_work_queue.py` adds core build, extension build and exact-core verification tasks with prerequisite ordering. A newly selected PostgreSQL minor replaces the old core target and requires extension verification against the new core bytes. Adding an extension creates its own build and verification tasks without changing unrelated target IDs.

Before a public release, `inventory.json` cannot describe candidate assets. The work queue can now accept an optional local candidate manifest. It opens each cached PostgreSQL or extension archive, checks its SHA-256 and embedded target identity, and reuses those exact bytes for the build task. A cached extension built for a prior minor in the same PostgreSQL major can be reused as an archive candidate, while verification against the newly selected core remains pending until exact applicable evidence exists. A retained record alone does not imply that its archive is retrievable. Actions run, artifact and expiry fields in the local manifest are claims for traceability; the planner does not authenticate them against GitHub. If local bytes are missing or mismatched, the queue requests a rebuild. Expiry of the original Actions artifact does not invalidate an already retrieved and checked local copy.

The planner produces deterministic bounded work and supports selection by project, platform, PostgreSQL major or exact item. It does not yet fetch candidate archives or dispatch the selected work to GitHub Actions. Many publication workflows also pin a prior core run ID and artifact with a short retention period; that pin is useful for reproducibility while available but must be refreshed or replaced when the artifact expires. This is the main missing link in an automatic add-version/add-extension flow. The local cache demonstrates safe reuse semantics, not a durable artifact service or publication orchestrator.

## Workflow layout and cost

The repository currently has 88 workflows: 86 support manual dispatch, 79 have a push trigger, and one reusable workflow scopes profile changes. The per-target wrappers make a failed target independently repeatable and keep its core pin explicit. They also duplicate target-specific YAML and path gates. Linux publication work is more grouped. The three-job extension trial workflow shows a small fan-out is practical: its passing jobs took 51–65 seconds each. There is no measured basis yet to replace the existing wrappers with a single fan-out workflow. A template or generated-wrapper check may remove duplication while preserving bounded retries; measure runner time, transfer and failed-target retry cost before changing job topology. The focused fresh-runner split adds one runner job because it closes an actual policy gap.

## Bounded Luna extension trials

Two Luna agents independently added feasibility scripts for pg_repack 1.5.3 and pg_partman 5.5.0, each scoped to Linux x86-64 with PostgreSQL 18.6. They found current-release and compatibility sources, used unmodified upstream PGXS builds, packaged project payloads, and wrote Alpine relocation, SQL and ELF checks. Both reported that the repository instructions were sufficient to design the path without a human decision. Root supervision set file boundaries, reviewed the output and kept both outside declared support. Their source digests are recorded after retrieval rather than pinned in shared support metadata.

Review caught the same version-rule mistake in both drafts: one treated pg_repack `1.5` as a major, while the other treated pg_partman major 5 as newly released within the last two years. [Upstream dates major 5 to September 2023](https://github.com/pgpartman/pg_partman/releases/tag/v5.0.0). Both research notes were corrected. The [extension onboarding guide](../adding-an-extension.md) now requires an upstream first-release date for each potentially relevant major. A third Luna agent read the guide and independently selected pg_squeeze 1.9.4, correctly identifying the 2016 start of major 1, then prepared a comparable Linux feasibility path. This demonstrates that the guidance improves version research; all three paths still require runtime checks.

The local Docker daemon was unavailable, so none of the three trials compiled or ran its behavioral verifier locally. Shell syntax and whitespace checks passed. The first [bounded CI run](https://github.com/BernieSumption/pg_binaries/actions/runs/39136361510) found that both initial PGXN source URLs returned 404. The [second run](https://github.com/BernieSumption/pg_binaries/actions/runs/39136529533) passed pg_partman but found missing PostgreSQL link libraries for pg_repack and a PostgreSQL 18 output-plugin configuration requirement for pg_squeeze. Root corrected the shared source URLs and Docker dependencies, then the pg_squeeze verifier configuration. The [third run](extension-autonomy-39136716680/README.md) passed all three builds, final-archive relocation and SQL probes, and ELF inspection. It consumed three standard Linux runner jobs of 51–65 seconds each. The three runs demonstrate that Luna can draft useful extension build paths, but source/version research and CI failures needed active review. A Luna agent should not independently declare an extension supported yet; it can take bounded implementation tasks under the guide and a reviewer should inspect source identity, metadata, dependencies and behavior.

## Verification and remaining decisions

The Python unit suite passed 669 tests after the cache and Windows workflow changes. Focused planner tests cover new extension targets, cached core and extension bytes, changed or missing bytes, and a new selected PostgreSQL minor's exact verification obligation. A planner run against the actual retained PostgreSQL 18.6 and pgvector 0.8.7 Linux x86-64 archives from [run 39081368117](https://github.com/BernieSumption/pg_binaries/actions/runs/39081368117) marked both build tasks reusable from checked local bytes while leaving current verification pending. The macOS fresh-runner workflow was manually dispatched against an unexpired pinned core artifact and passed in [run 39135932527](hypopg-macos-publication-39135932527/README.md). Its compact attempt, receipt, static report, SQL output and archive-bound record are retained. The first Windows split-workflow run passed archive checks but failed evidence import because the new verifier put reports in a separate directory. After correcting the handoff, [run 39137163791](hypopg-windows-publication-39137163791/README.md) passed both jobs and imported its archive-bound record. The downloaded core and HypoPG SHA-256 values match that record.

The tooling is ready for small, reviewed batches of extension feasibility work, including Luna-authored build paths. It is not ready for unattended expansion across the selected matrix or for treating the selected set as release-eligible. Complete the fresh-runner split for the remaining macOS and Windows extension workflows, establish a durable way to retrieve or rebuild candidate archives after temporary artifacts expire, and connect bounded planner items to dispatchable workflows. These are development tasks under the existing specification; no change to release scope is implied.
