# Selected Windows core dependency redistribution review

On 2026-10-20, the selected PostgreSQL 18.6 Windows x86-64 archive from [run 39444631332](https://github.com/BernieSumption/pg_binaries/actions/runs/39444631332) matched SHA-256 `7dee5b25cde652310715b8e46d7af66279e0d532c7996e6db674efd090a21b83`. The retained [DLL map](vcpkg-dll-map.json) and [component inventory](core-license-inventory.json) were extracted from those exact archive bytes. The map attributes 16 bundled DLLs to eight versioned vcpkg ports; the inventory still marks their combined redistribution review pending. Other PostgreSQL majors require their own final-archive checks before publication.

The pinned [vcpkg libiconv 1.19 port](https://github.com/microsoft/vcpkg/blob/9e593bb18ea69cc5095e012465dcd675a822ed0d/ports/libiconv/portfile.cmake) builds GNU libiconv on Windows from a checksum-pinned source archive and applies three distribution patches. Its packaged notice, `LICENSES/dependencies/libiconv.txt`, states that `iconv-2.dll` and `charset-1.dll` are LGPL libraries. The included LGPL-2.1 text requires corresponding source for redistributed library object code, or equivalent source access from the same distribution place. The current core archive contains the licence text but no corresponding libiconv source or patches. This is a concrete publication blocker for these two DLLs, independent of their successful runtime tests. The port's GPL notice covers its separately licensed iconv program and documentation; neither program nor documentation is among the mapped DLL payloads.

The mapped `zstd.dll` is zstd 1.5.7. The [pinned vcpkg port](https://github.com/microsoft/vcpkg/blob/9e593bb18ea69cc5095e012465dcd675a822ed0d/ports/zstd/portfile.cmake) builds the shared library with upstream CMake defaults and packages the top-level BSD/GPL texts. [Upstream CMake](https://github.com/facebook/zstd/blob/v1.5.7/build/cmake/lib/CMakeLists.txt) enables the dictionary builder by default and includes every `lib/dictBuilder/*.c` file in that library. The included [`divsufsort.c`](https://github.com/facebook/zstd/blob/v1.5.7/lib/dictBuilder/divsufsort.c) carries a separate Yuta Mori copyright and permission notice. Direct inspection of this exact core archive found only the top-level BSD/GPL texts in `LICENSES/dependencies/zstd.txt`; it did not find the divsufsort notice. Supply the exact upstream notice with the archive and map it to `zstd.dll` before resolving that component. This is an additional concrete redistribution gap, not a claim that zstd requires source delivery.

The mapped `libxml2.dll` is libxml2 2.15.3. Its [upstream Copyright](https://raw.githubusercontent.com/GNOME/libxml2/v2.15.3/Copyright) identifies [`dict.c`](https://raw.githubusercontent.com/GNOME/libxml2/v2.15.3/dict.c) and [`list.c`](https://raw.githubusercontent.com/GNOME/libxml2/v2.15.3/list.c) as carrying separate copyright and permission notices. The inspected archive's `LICENSES/dependencies/libxml2.txt` contains the general notice but omits those two file notices. They are library source files and likely contribute to the ordinary `libxml2.dll` build; object membership has not yet been checked. The builder now stages their exact upstream headers as additional notices and checks the mapped 2.15.3 version. Verify them in a rebuilt archive before resolving this component.

The same exact archive maps ICU 78.3, OpenSSL 3.6.3, zlib 1.3.2, LZ4 1.10.0 and libxslt 1.1.45 DLLs to included vcpkg notices. Review on 2026-10-20 found no source-delivery requirement or concrete missing notice for those library payloads under their [ICU](https://unicode-org.github.io/icu/userguide/icu/release.html), [OpenSSL](https://github.com/openssl/openssl/tree/openssl-3.6.3), [zlib](https://zlib.net/zlib_license.html), [LZ4 library](https://raw.githubusercontent.com/lz4/lz4/v1.10.0/lib/LICENSE) and [libxslt](https://raw.githubusercontent.com/GNOME/libxslt/v1.1.45/Copyright) terms. These are candidate findings: exact source-to-DLL provenance and final archive notice bytes still need checking before replacing the aggregate pending review. The packaged ICU notice includes its Unicode, ICU and third-party sections; a byte-for-byte comparison to the upstream 78.3 file was unavailable. The OpenSSL 3.6.3 source root has no `NOTICE` file.

A candidate source-delivery route is to publish a separate source asset beside the binary archive, containing the exact GNU libiconv 1.19 source archive, the three applied vcpkg patches and its portfile. The pinned [portfile](https://github.com/microsoft/vcpkg/blob/9e593bb18ea69cc5095e012465dcd675a822ed0d/ports/libiconv/portfile.cmake) records the source SHA-512, patch names and configure options. Although `policies/releases.md` permits source links, the [FSF GPLv2 distribution FAQ](https://www.gnu.org/licenses/old-licenses/gpl-2.0-faq.html) says a link to source hosted elsewhere needs an arrangement that keeps it available for as long as the binary; merely pointing to currently available upstream files is insufficient for the same-place option. The libiconv libraries use LGPL-2.1, whose object-code clause also specifies equivalent access from the same place. A companion asset under our control avoids relying on external retention. Verify their identities and availability before marking libiconv resolved. This avoids adding development-only source to every PostgreSQL download. The current release policy and tooling do not yet stage such a companion asset, so this remains implementation work. Review the other seven ports against their exact packaged notices and source identities, then replace the aggregate pending component with version-keyed DLL components. No public download or redistribution decision is claimed by this note.
