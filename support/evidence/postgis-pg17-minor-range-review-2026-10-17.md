# PostGIS 3.6.4 on PostgreSQL 17.7–17.11

A PostGIS archive built against PostgreSQL 17.11 can claim the 17.7–17.11 range only after the same archive bytes pass the required tests with both exact core versions and no known intermediate incompatibility applies.

[PostgreSQL 17's extension ABI guidance](https://www.postgresql.org/docs/17/extend-compat.html) says an extension compiled against one minor release should generally work with other minors of the same major, while rare exceptions are documented in release notes. [PostGIS 3.6's installation manual](https://postgis.net/docs/manual-3.6/postgis_installation.html) includes PostgreSQL 17 among its supported build majors. The [17.8](https://www.postgresql.org/docs/17/release-17-8.html), [17.9](https://www.postgresql.org/docs/17/release-17-9.html) and [17.10](https://www.postgresql.org/docs/17/release-17-10.html) notes reviewed on 2026-10-17 did not identify an intermediate extension ABI break. An earlier [17.2 correction](https://www.postgresql.org/docs/17/release-17-2.html) shows why the ABI policy alone is insufficient evidence.

Inference: the reviewed upstream material contains no known intermediate incompatibility for 17.7–17.11. [Run 39018319216](https://github.com/BernieSumption/pg_binaries/actions/runs/39018319216) then passed the same PostGIS 3.6.4 Linux x86-64 archive with exact PostgreSQL 17.7 and 17.11 cores on clean Ubuntu 24.04, older/no-glibc containers and Linux 5.15 guests. Its 16 current-profile pilot records bind the shared extension checksum and the endpoint-specific core checksums. This supports the candidate range under the repository's endpoint rule; publication-profile evidence and the rest of the declared platforms remain separate work.
