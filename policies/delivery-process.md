# Delivering declared support

Clients need every stable PostgreSQL release required by the functional specification and enough extension packages to execute their intended schemas. A support target is a PostgreSQL version, extension version, operating system, architecture and, for a reusable extension archive, PostgreSQL compatibility range. The support declaration describes intended targets. `inventory.json` describes only public downloads that passed verification.

## Declare and reconcile support

`support.json` at the repository root is the machine-readable source of intended platform targets and extension releases. It records the OS minima chosen in [os-support.md](os-support.md), supported PostgreSQL major range and release cutoff from the functional specification, included extension projects and SQL names, selected version lines, prerequisites, and upstream compatibility restrictions. The policies explain decisions; a target must not be silently omitted from `support.json` because it is difficult to build.

An extension version may declare `operating_systems` as a nonempty list of supported OS keys when upstream documents a narrower OS subset. Omission targets every declared OS. Each selected OS targets the architectures declared for that OS in `support.json`; extension-specific architecture subsets are not permitted. PostgreSQL minimum and maximum major fields describe documented compatibility restrictions. Omission of a maximum keeps future stable majors visible as unmet until evidence supports them.

For PostgreSQL, the support declaration expresses the stable-release rule, not a hand-maintained list of every minor version. A discovery step obtains the dated upstream stable-release list and expands the rule into an exact target snapshot. The snapshot, its upstream source and retrieval date are retained with each coverage report. New qualifying stable releases become unmet requirements as soon as discovery sees them. Prereleases and major versions below 15 are rejected.

To add or change support, an agent edits `support.json` and the relevant decision policy, if the decision changed. For a new PostgreSQL release covered by the existing rule, the agent refreshes discovery rather than adding the version by hand. The reconciliation command compares the expanded intended targets, public inventory, candidate archives and verification records. It reports required targets with no archive and archives awaiting verification. It also retains each failed or skipped verification record under its outcome, with the target and check identifiers, so these records remain visible without counting as passes. The report must return failure when a required target lacks a verified public download; an incomplete run must not disappear from later reports.

## Plan builds and checks

The planner derives work from unmet targets and existing archive evidence. It may reuse one extension archive across PostgreSQL versions only when upstream documents the claimed range and endpoint tests pass; a known intermediate failure splits the range. It chooses the smallest defensible set of extension builds and uses standard GitHub-hosted runners for the target platforms. Workflows invoke the planner's generated jobs rather than containing independent version lists. Build outputs and test records are keyed by source inputs, archive checksum, test revision and verification environment so unchanged applicable results can be reused. The [testing policy](testing.md) defines eligibility checks.

The planner must show all proposed work before expensive CI dispatch. Failed jobs retain their target and reason in coverage output. Build and verification records are retained longer than temporary Actions artifacts, with enough information to retrieve or rebuild the exact archives. A candidate draft retains the verification records used for each new immutable archive URL; local preflight checks their archive SHA-256 against the staged bytes. This checksum link is structural evidence, not a publication eligibility decision. Runner time, matrix size and artifact storage are monitored; if the required work cannot reasonably fit standard runners, the problem goes to `HUMAN_REVIEW_QUEUE.md`.

The candidate extension archive planner groups declared SQL-name targets by project, selected extension version, platform and PostgreSQL major. It reports the exact covered PostgreSQL minors and their endpoints, leaving every group unverified. A major boundary is kept separate because native extension binaries cannot be assumed to share a PostgreSQL server ABI across majors. A group is a planning unit, not evidence that one archive can serve every listed minor; the build and endpoint checks must establish that range before inventory may claim it.

## Publish verified downloads

An archive becomes eligible for a public inventory only after the final bytes pass the required checks, including relocation, minimum and current OS testing, licensing and documented extension compatibility. The publisher generates a candidate inventory from eligible bytes plus unchanged public entries, preserving their URLs. It follows [releases.md](releases.md) to upload assets before publishing the new inventory and then runs anonymous public-download verification. Publication requires separate authorization; until then, eligible candidate archives remain visibly unpublished and `inventory.json` must contain no temporary Actions URLs.

For example, when upstream publishes a qualifying PostgreSQL 18.7, discovery adds five OS and architecture targets to the expanded support snapshot. Reconciliation shows all five missing until archives exist. The planner builds and tests them on the relevant runners and checks whether existing extension archives claiming a range through 18.7 remain applicable. Verified new archives become candidate inventory entries, while unchanged extension downloads keep their older release URLs. Publication makes the new inventory current only after its referenced archives are available.

The Linux pilots select one declared PostgreSQL 15 through 18 minor per architecture from the planner, choosing the highest missing target without current-profile pilot evidence at both OS endpoints when a push supplies no version. The x86-64 and arm64 pilots run on standard native Ubuntu runners and then verify the same archives in Linux 5.15 QEMU guests. The macOS and Windows pilots also select one declared core target per platform from `support.json`; without an explicit dispatch version, they skip only targets with retained current-profile pilot evidence for their current OS checks. Their minimum OS endpoints remain unresolved. All current external-extension pilot builds still use selected extension versions rather than a general extension work planner. These runs do not establish coverage for the declared product matrix. `support.json` and `tools/coverage.py` expose intended targets, missing public downloads and downloads awaiting verification. `tools/plan_work.py` derives target-level build and verification work from those states. `tools/candidate_inventory.py` merges proposed immutable URLs with retained public entries into a structural draft and keeps the proposed verification records by URL. A project-level proposal may reference one extension archive under every SQL name it provides, with separate endpoint evidence for each name and one URL-keyed archive checksum. Its inline evidence claims and incomplete metadata do not establish publication eligibility. The verification-record parser binds records to checked-in test profiles and treats outdated suites as stale. The separate QEMU workflows are available only for manual feasibility runs. All registered profiles remain pilots, and no publication profile exists yet. The local preflight checks candidate schema and OS minima, intended target presence, unchanged public references, verification-record checksums, staged archive bytes, built-in extension claims, extension metadata, and declared licence evidence. It does not establish behavioural evidence, legal sufficiency or public availability. The planner does not yet account for unpublished candidate archives, reuse, failed or skipped work, CI dispatch or public-download checks. Publication orchestration does not yet exist; pilot success records are not coverage evidence for the declared product.

The PostGIS Linux pilot attempts to reuse a successful same-revision PostgreSQL 18.6 core archive for each matching architecture only when the archive checksum and current verification profile match. It builds the core independently if the short-lived artifact is unavailable or fails validation. The same-revision condition currently forces a new core build after any commit, even when the builder code is unchanged.
