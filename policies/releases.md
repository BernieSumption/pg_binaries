# Release layout and publication

Clients obtain `inventory.json` from `https://github.com/BernieSumption/pg_binaries/releases/latest/download/inventory.json`. It lists public archives and their SHA-256 values in the format defined by [the functional specification](../specs/functional.md). A release becomes current only after every URL in its inventory is available.

## Names and immutable downloads

Each published release receives a new tag of the form `catalog-YYYYMMDD-N`, where `N` increases for multiple releases on one date. Core archives use `postgresql-<version>-<platform>-<architecture>.tar.gz`. Extension archives use `<project>-<version>-postgresql-<build-version>-<platform>-<architecture>.tar.gz`, with the build version identifying the core used to produce the package. Existing range-named archives may be retained when selected and verified; new builds do not need to discover historical-minor ranges. In archive names and extension payload roots, `<project>` is the lower-case project name with each run of non-alphanumeric characters replaced by `_`, trimmed at both ends; for example, `PostGIS TIGER Geocoder` becomes `postgis_tiger_geocoder`. The inventory alone advertises the verified PostgreSQL range for an extension download. A release URL includes its tag and archive name. The SHA-256 in the inventory identifies the exact bytes. A corrected archive must receive a new URL; never replace or rename an asset at an existing URL.

The current inventory in the repository root is the source-controlled record of public availability. An unpublished candidate inventory must be kept separately and must not claim that temporary CI artifacts are public downloads. `tools/candidate_inventory.py` generates a structural draft from explicit base inventory, proposal, intended-support, and release-snapshot files; its output is not a publication claim. Each new release contains `inventory.json` and only the binary archives added or changed in that release. Omit entries that no longer qualify under the version selection rule; unchanged entries that remain selected retain URLs on older tags; their assets must remain publicly available while referenced. A release tag or asset referenced by the current inventory must not be deleted or edited.

## Publication order

Generate a candidate inventory from the currently selected support targets, verified archive bytes, and still-selected entries in the existing public inventory. Record why superseded entries leave the candidate; an unbuilt or failed selected target cannot be removed to make coverage pass. Check its schema, coverage claims, URLs, checksums, archive metadata and licence pointer, and retained references. Upload new immutable archives and the candidate inventory to a new draft release. Check the uploaded assets and checksums while the draft is not the latest public release. Publish the draft as the latest release only after every referenced new and old archive is available. If an upload or check fails, leave the previous latest release intact; retry on a new tag if a published URL would otherwise change bytes.

Immediately after publication, run the anonymous download verification in [testing.md](testing.md) against the public `latest` inventory, including archives on older tags. Record the result and repair any failure with a new release and new URLs. A local dry run can test generation, ordering, retained references and failure handling, but it cannot establish public accessibility.

`tools/local_publication_dry_run.py` models publication order after candidate generation and preflight with a filesystem-backed store. It stages archive bytes and the candidate inventory under a new tag, verifies every candidate URL and checksum against new or retained local assets, and switches the current inventory only after verification. Its tests inject failures around promotion and retrieve all promoted references from the local store. The tool never calls GitHub and does not test anonymous network access; only the post-publication check above can establish that clients can download public assets.

The existing workflows publish only temporary Actions artifacts. Their local preflight still checks the previous OS and PostgreSQL endpoint contract. Update it to require the [current verification evidence](testing.md) for every selected core/extension combination and to permit policy-driven inventory retirement. Exact assembled core and prerequisite checksums remain mandatory. This is tracked in [the migration backlog](../GOAL_BACKLOG.md#version-policy-migration); a passing old preflight is not evidence that the new contract is implemented.

## Licence pointer

The central [`LICENSES.md`](../LICENSES.md) lists each redistributed dependency, its declared licence and links to the source declaration. Every download must contain a `LICENCE` file pointing to `https://github.com/BernieSumption/pg_binaries/blob/main/LICENSES.md`. Verify the exact pointer in each staged archive with [`tools/license_pointer.py`](../tools/license_pointer.py). Licence acceptability and human-reviewed exceptions follow [licenses.md](licenses.md); publication does not require per-archive licence inventories, copied licence texts, source offers or source-link reviews.

`tools/publication_preflight.py` checks each new archive's name against the component, version, platform and PostgreSQL build target or range claimed by the candidate. For PostgreSQL archives it checks the target and built-in names in `manifest.json` against the candidate and packaged controls. For extension archives it checks project, version, target operating system and architecture, PostgreSQL build version, SQL names and prerequisites against intended support and the candidate. An exact-version filename must match the metadata's build version; a range filename must contain it. One project archive URL may serve several SQL extension names from that project. Retained archive references are not re-reviewed by this local gate.
