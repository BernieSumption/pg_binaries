# Release layout and publication

Clients obtain `inventory.json` from `https://github.com/BernieSumption/pg_binaries/releases/latest/download/inventory.json`. It lists public archives and their SHA-256 values in the format defined by [the functional specification](../specs/functional.md). A release becomes current only after every URL in its inventory is available.

## Names and immutable downloads

Each published release receives a new tag of the form `catalog-YYYYMMDD-N`, where `N` increases for multiple releases on one date. Core archives use `postgresql-<version>-<platform>-<architecture>.tar.gz`. Extension archives use `<project>-<version>-postgresql-<build-version>-<platform>-<architecture>.tar.gz`, with the build version identifying the core used to produce the package. Existing range-named archives may be retained when selected and verified; new builds do not need to discover historical-minor ranges. In archive names and extension payload roots, `<project>` is the lower-case project name with each run of non-alphanumeric characters replaced by `_`, trimmed at both ends; for example, `PostGIS TIGER Geocoder` becomes `postgis_tiger_geocoder`. The inventory alone advertises the verified PostgreSQL range for an extension download. A release URL includes its tag and archive name. The SHA-256 in the inventory identifies the exact bytes. A corrected archive must receive a new URL; never replace or rename an asset at an existing URL.

The current inventory in the repository root is the source-controlled record of public availability. An unpublished candidate inventory must be kept separately and must not claim that temporary CI artifacts are public downloads. `tools/candidate_inventory.py` generates a structural draft from explicit base inventory, proposal, intended-support, and release-snapshot files; its output is not a publication claim. Each new release contains `inventory.json` and only the binary archives added or changed in that release. Omit entries that no longer qualify under the version selection rule; unchanged entries that remain selected retain URLs on older tags; their assets must remain publicly available while referenced. A release tag or asset referenced by the current inventory must not be deleted or edited.

## Publication order

Generate a candidate inventory from the currently selected support targets, verified archive bytes, and still-selected entries in the existing public inventory. Record why superseded entries leave the candidate; an unbuilt or failed selected target cannot be removed to make coverage pass. Check its schema, coverage claims, URLs, checksums, installation metadata, licences, and retained references. Upload new immutable archives and the candidate inventory to a new draft release. Check the uploaded assets and checksums while the draft is not the latest public release. Publish the draft as the latest release only after every referenced new and old archive is available. If an upload or check fails, leave the previous latest release intact; retry on a new tag if a published URL would otherwise change bytes.

Immediately after publication, run the anonymous download verification in [testing.md](testing.md) against the public `latest` inventory, including archives on older tags. Record the result and repair any failure with a new release and new URLs. A local dry run can test generation, ordering, retained references and failure handling, but it cannot establish public accessibility.

`tools/local_publication_dry_run.py` models publication order after candidate generation and preflight with a filesystem-backed store. It stages archive bytes and the candidate inventory under a new tag, verifies every candidate URL and checksum against new or retained local assets, and switches the current inventory only after verification. Its tests inject failures around promotion and retrieve all promoted references from the local store. The tool never calls GitHub and does not test anonymous network access; only the post-publication check above can establish that clients can download public assets.

The existing workflows publish only temporary Actions artifacts. Their local preflight still checks the previous OS and PostgreSQL endpoint contract. Update it to require the [current verification evidence](testing.md) for every selected core/extension combination and to permit policy-driven inventory retirement. Exact assembled core and prerequisite checksums remain mandatory. This is tracked in [the migration backlog](../GOAL_BACKLOG.md#version-policy-migration); a passing old preflight is not evidence that the new contract is implemented.

## Redistribution review before publication

Every new staged archive must include `<root>/LICENSES/inventory.json` with `schema_version: 1` and a non-empty `components` list. An extension archive may instead use `<root>/LICENSES/<root>-inventory.json` so that copying its payload into the PostgreSQL prefix does not collide with the core inventory. Each component must identify `component`, `version`, non-empty archive-relative `payload_paths`, and `license_file`; `additional_license_files` may list further required texts and notices. Licence paths are relative to `LICENSES`, or may start with `LICENSES/`. Declared evidence must be included as non-empty regular files. Payload paths must identify an archive member or a directory containing members. The gate reads archive members without extracting them and rejects duplicate members and unsafe paths.

Each component must have `redistribution_review` with `status: resolved`, a non-empty `basis` describing the reviewed terms and their application to this distribution, and one explicit `source_obligation`:

- `none`: the review found no source-delivery obligation for this distribution.
- `source-links`: `source_links` must list public HTTPS URLs for the source required by the reviewed terms, including applicable modifications and build material.
- `source-offer`: `source_offer_file` must identify an included non-empty offer text under `LICENSES`.

A pending, blocked or absent review fails preflight. Existing provenance fields such as `source_url`, `source_urls` and `license_source` do not establish a resolved review or satisfy the explicit source-link declaration. Reviewers must determine which texts, notices, source material or offers the terms require and record the disposition; adding a URL alone does not resolve those obligations.

When an upstream repository states a licence for the repository and gives no separate terms for a data file it contains, apply that repository licence to the data file and outputs derived from it. Do not investigate whether upstream had the right to apply its stated licence to the data's earlier sources. Explicit separate file or dataset terms still require their own review. Record the repository licence and this assumption in the component's redistribution review.

The user reviewed Microsoft's [Visual Studio 2022 licence terms](https://visualstudio.microsoft.com/license-terms/) and [redistributable-file list](https://learn.microsoft.com/en-us/visualstudio/releases/2022/redistribution#visual-c-runtime-files) and determined that the Visual C++ toolset may be used for this open-source build and its listed, unmodified runtime DLLs may be redistributed with it. The review found no requirement to include a copy of Microsoft's licence file. Windows archives must nevertheless include the [project's runtime notice](../scripts/windows/MSVC-RUNTIME.md), rendered with the exact bundled DLL names, beside the PostgreSQL executables and under `LICENSES/`. Record the selected DLL names and versions in the archive's component inventory before publication. This human decision resolves the Visual C++ licence question; archive dependency checks and current-runner verification remain required; clean-consumer-machine execution belongs to the proposed manual post-release process.

`tools/publication_preflight.py` accepts paths to the base and candidate inventories, intended support, release snapshot, and staged-assets manifest; it checks these declarations and local evidence against the staged archive bytes. For each new archive it checks that the asset filename identifies the component, version, platform and PostgreSQL build target or range claimed by the candidate. For PostgreSQL archives it also checks the target and built-in names in `manifest.json` against the candidate and packaged controls. For extension archives it accepts the project payload directory with only a sibling `metadata.json` and checks project, version, target operating system and architecture, PostgreSQL build version, SQL names and prerequisites against intended support and the candidate. An exact-version filename must match the metadata's build version; a range filename must contain it. One project archive URL may serve several SQL extension names from that project. Its `redistribution_review_status: declarations-checked` result establishes structural completeness only. It does not determine whether a licence interpretation is correct, whether every redistributed component has been identified, whether a source offer is legally sufficient, or whether a source URL is available and supplies all required material. Those remain publication checks under the publication order above. Retained archive references are not re-reviewed by this local gate.

Current pilot licence inventories use several formats and generally omit explicit redistribution reviews; some archives have only licence texts. The Linux PostgreSQL writer now records the installed binary package and exact source-package identities for every bundled runtime component, but source identity alone does not determine the applicable obligations or supply required source material. The inventories must be normalized and reviewed before passing this gate. Their existing provenance and passing runtime tests do not establish publication eligibility.
