# Verification of packaged downloads

Clients use downloaded archives to create and inspect PostgreSQL schemas. Verification must run against final archive bytes, using the installation procedure in [install-process.md](install-process.md), because a successful build does not establish that a client can use the package.

## Evidence and eligibility

Each verification record must identify archive SHA-256, source and component versions, test revision, operating system and architecture, environment image or runner version, test cases, and outcome. A failure, skip, missing record, or record for different bytes or tests must not satisfy a claim. A build and its verification may be reused only when their inputs and claimed compatibility remain applicable. The coverage report described in [delivery-process.md](delivery-process.md) must distinguish missing intended coverage from broken published downloads.

The Linux PostgreSQL pilot archive includes `LICENSES/inventory.json`. Its component entries identify the PostgreSQL or runtime package version, the PostgreSQL payload directories or exact copied runtime library paths, the included license text, and a source URL. The bundled glibc and static launcher entries also identify exact source-package versions and source archives; the glibc entry lists referenced licence texts. The archive carries standard licence texts referenced by package copyright files. The archive verifier checks that mapped files and licence texts exist in the extracted archive and that every copied runtime library and launcher binary has exactly one package mapping. This checks archive provenance and mapping completeness; it does not determine whether a licence permits redistribution. The inventory writer may attach explicit redistribution reviews keyed by exact component, package and version; when a review file is supplied it must cover every packaged component with a resolved decision. Without that file the pilot inventory remains provenance-only and cannot pass publication preflight. A fixture archive generated with complete review declarations passes the preflight's structural check; this does not establish that any actual component's terms have been reviewed.
The PostGIS Linux pilot also includes `LICENSES/postgis/inventory.json`. It maps the selected SQL modules, extension scripts, each copied runtime library, and the PROJ and GDAL data directories to the PostGIS or Ubuntu package version, included licence text, and exact-version source link. Runtime libraries already present in the PostgreSQL archive must match byte-for-byte after runtime-path patching and are covered by the core inventory. The PostGIS entry records the downloaded source archive's SHA-256. The archive includes the standard licence texts referenced by package copyright files. Its verifier checks these mappings and referenced texts against the extracted payload; a source URL is evidence of where to obtain source, not a legal conclusion about redistribution. Successful CI checks emit one `pilot-smoke` record for each of the four tested SQL extensions, bound to both the PostGIS and assembled PostgreSQL archive checksums, the PostGIS test profile, and clean verification environments. These records do not qualify the archive for publication.

Records must distinguish pilot smoke checks from publication checks. A publication record must give one `passed`, `failed`, or `skipped` result for every case in its profile, with no extra cases; its aggregate outcome must follow those results. A passing publication record must name a full test commit, unique case identifiers, the verification image, and the runtime dependency-check profile and result. An extension publication record must also name the exact PostgreSQL archive used for assembly. Candidate generation and coverage compare its checksum with the core download claimed for each tested PostgreSQL endpoint; a version match alone cannot establish that the advertised archives work together. When an extension declares another extension project as a prerequisite, its publication receipt and record must also bind that project's exact archive filename, version and SHA-256. Candidate generation, coverage and preflight must match each prerequisite claim to the corresponding downloadable archive for the tested PostgreSQL endpoint. Pilot records remain useful for development but must not satisfy publication coverage. The profile registry binds each record to a named case set and the current content of its test sources. macOS and Windows builder scripts are excluded from test-profile hashes because archive checksums and build revisions identify the bytes separately; an unchanged test suite remains applicable to previously tested archive bytes after a build-only edit. UTF-8 text line endings are normalized to LF before hashing so identical Windows and Unix checkouts have the same profile revision; binary sources remain byte-exact. Earlier all-CRLF profile digests remain applicable only while their normalized source content matches. A changed suite makes old records stale without discarding them. The Linux x86-64 and arm64 publication profiles identify the current-OS archive, runtime-portability and diagnostic checks, and the minimum-OS full archive suite in a Linux 5.15 guest. The workflow must write each endpoint's CI step outcomes before checking for archive bytes or guest identity, so failed and skipped attempts remain in its uploaded evidence even when it cannot emit a checksum-bound record. `tools/create_linux_publication_receipt.py` maps those outcomes to complete case receipts only when the required bytes and environment identity exist; `tools/emit_linux_publication_records.py` then validates the receipts and exact PostgreSQL and pgvector archive bytes before writing passed, failed or skipped records. `tools/create_extension_publication_receipt.py` maps named extension verification steps to a complete receipt. `tools/emit_extension_publication_records.py` validates its declared PostgreSQL and extension target, exact assembled core and extension archive checksums, package metadata, archive range and CI revision before emitting one record per declared SQL name. Before an archive is eligible for publication, a verifier outside its build environment must assemble the installation from archives and metadata alone. The verification environment must not supply development files or unbundled runtime libraries that conceal missing dependencies. A fresh job on a developer-equipped image, by itself, does not establish this property. Record the exact operating system and runtime dependency checks used to establish it.

For each supported OS and architecture, verify the minimum supported OS and a current supported OS. For an extension archive claiming a PostgreSQL range, verify both range endpoints. A known incompatible intermediate version splits the range even if its endpoints pass. A new PostgreSQL release, OS baseline, dependency, or test revision must invalidate only the evidence it affects; unchanged applicable results may be reused.

## PostgreSQL and extension behaviour

From the extracted archive, run `initdb` as an ordinary user with UTF-8 encoding, start `postgres` with `pg_ctl`, connect through packaged `psql`, apply representative types, collations, defaults, constraints, indexes, views, functions and procedures, inspect the resulting definitions through catalogues, and stop cleanly. Exercise `pg_dump` and restore the dump with `pg_restore` into a new database, then verify restored definitions. The Linux verifier checks a restored schema, function, view, check constraint and valid partial index in the catalogues as well as representative data and function results. Assert expected results rather than relying on a zero exit status or printed output alone.

Discover included built-in SQL extensions from the final PostgreSQL archive and verify the inventory claim against that discovery. Exercise representative schema behaviour for each advertised built-in extension and enabled option. For each external SQL extension, create the extension, use at least one of its objects in DDL, execute a representative operation, and check its result. Where an intended extension version selects a higher available version, run representative DDL written for the intended version against the selected final archive on the required OS and PostgreSQL endpoints. Include the latest intended version before each documented or assumed compatibility break; a passing smoke test cannot override a known upstream incompatibility. The shared pgvector case creates a vector column and HNSW index, confirms the index uses the HNSW access method, and checks a nearest-neighbour result on each pilot OS. These checks detect packaging and compatibility failures; they do not replace upstream's full test suite. Verify version, prerequisite and platform claims against archive metadata, documented upstream compatibility, and endpoint results. The pgvector case tests its selected 0.8.7 release; it does not establish a next-higher extension-version boundary because no second pgvector version is selected.

Assemble PostgreSQL and extensions with the documented copy procedure as an ordinary user in a user-writable directory, run representative operations, move the assembled installation, make the old path unavailable, and repeat the operations. Check required data files and library loading after relocation. An agent review of the test installer must confirm that it follows [install-process.md](install-process.md) without undeclared setup. The [Linux installer review](../support/evidence/linux-installer-review-2026-10-17.md) found that the verifier extracts both archives, merges the extension payload and moves the installation prefix as the `postgres` user. ## Diagnostics and published bytes

Follow [debugging.md](debugging.md) to collect a representative server log error and a system-level loader or crash failure. Verify that retained evidence lets a maintainer identify the archive and investigate the failure, including symbol resolution where applicable.

After a release, retrieve `inventory.json` anonymously from the public latest-release URL. Download every referenced archive, including those on older releases, verify its checksum, and compare its bytes with the archive that passed pre-publication tests. A local candidate inventory cannot substitute for this published-download check.
