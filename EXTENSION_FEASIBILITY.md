# Adding an extension

An extension feasibility task determines whether one upstream project can produce a usable archive for a declared PostgreSQL and platform target. It may end with a research finding, a build script, or a failed build. It does not add the project to advertised support until the selected target and final archive pass the requirements in the [functional specification](specs/functional.md), [testing specification](specs/testing.md), and [delivery policy](policies/delivery-process.md).

Before changing code, read `AGENTS.md`, the [extension selection policy](policies/extensions.md), any working path for the same project, and a comparable path on the target platform. Record the upstream release source, licence, PostgreSQL and OS support, optional dependencies and any limits. Apply the shared version rule using the date when each **major** first appeared. A minor release such as `1.5` within major `1` is not a new major. Cite the first tag or another upstream release record for each major that might fall within the two-year window; do not infer its age from the newest patch date. Record an unresolved selection in `HUMAN_REVIEW_QUEUE.md` only when the criteria cannot be resolved under the specifications and policies.

Follow [the architecture policy's recipe development sequence](policies/architecture.md#developing-a-new-recipe) when choosing a local prototype and references for a platform port.

For a bounded trial, choose one exact PostgreSQL release, OS and architecture. Build unmodified upstream source using its documented mechanism, pin the source digest before selecting it for support, and package only the required payload with upstream notices and metadata. Keep experimental output visibly outside `support.json` until it is reviewed. The build may run on the local computer only inside Docker; targets Docker cannot build belong on a standard GitHub-hosted runner.

Verification consumes the final archive and the exact PostgreSQL archive in the environment required by [the testing policy](policies/testing.md). Check hashes, payload layout, copy collisions, native dependencies, ordinary-user startup, representative schema DDL and behavior, then move the installation and repeat representative operations. A successful source-tree test or shell syntax check does not establish archive usability. Preserve failed attempts and distinguish checks that ran from checks blocked by an unavailable environment.

Report the source and target identity, inclusion decision, files changed, commands and CI runs, archive checksums, case outcomes, limits and remaining work. State separately whether the result is a draft, a verified candidate, or eligible to be considered for advertised support. Policy and implementation changes must be committed together; specifications remain human-managed.
