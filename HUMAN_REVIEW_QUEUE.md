# Human review queue

## Windows Visual C++ runtime redistribution

The Windows x86-64 pilot passes on Windows Server 2022, but its archive omits `VCRUNTIME140.dll` even though `postgres.exe` imports it. The runner has the Visual C++ runtime installed, so that result does not establish the [functional specification's](specs/functional.md) clean-machine installation guarantee. The archive must not be advertised as self-contained yet.

App-local bundling of the required non-UCRT DLLs is the preferred technical approach. [Microsoft permits placing individual redistributable DLLs beside application executables](https://learn.microsoft.com/en-us/cpp/windows/redistributing-visual-cpp-files?view=msvc-170), so no installer is needed. Static `/MT` linking would require PostgreSQL and every linked dependency to use a consistent runtime mode and is more disruptive to the present build. The build should derive the DLL closure from all archive executables and libraries, bundle only required files, and test their resolution on a clean Windows host. Windows 10 and later supply the [Universal CRT](https://learn.microsoft.com/en-us/cpp/windows/universal-crt-deployment?view=msvc-170).

Decision needed: Which Visual Studio licence covers the project's build and release operator, and does it authorize public redistribution of those individual DLLs? [Microsoft limits redistribution to licensed Visual Studio users under the applicable terms](https://learn.microsoft.com/en-us/cpp/windows/redistributing-visual-cpp-files?view=msvc-170). Its [Community licence guidance](https://www.microsoft.com/licensing/guidance/Visual-Studio) offers an open-source-project route, but the public repository and GitHub runner's installed Visual Studio do not establish which licence applies to this operator. Once entitlement is confirmed, implement and verify app-local bundling; no installation prerequisite is acceptable.

Answer: This question is phrased as a request for licencing permission, but there seems to be an unresolved technical issue behind it. First of all, determine what the preferred technical solution would be. Would we prefer to statically link or to bundle? If we bundle the Visual C++ redistributable, it is a package that needs to be installed, or a DLL that can ship in the folder and run locally? An installation is not acceptable, a DLL is. Establish the clear recommended technical solution, and then if this is blocked on a licence uncertainty, come back to me with that question By updating this item in the queue. If the preferred technical solution does not have a licence uncertainty, and feel free to research this yourself, then just implement it, and then you can remove this item from the queue.

## Linux user-space compatibility floor

The [functional specification](specs/functional.md) requires one Linux archive per architecture to work across supported machines without non-universal external dependencies. The [OS policy](policies/os-support.md) states only a kernel 5.15 minimum. A kernel version does not identify the C library or dynamic loader. The earlier Linux pilot used Ubuntu 22.04 and left glibc and the ELF loader outside the archive. A clean machine with kernel 5.15 and an older or different libc could fail before PostgreSQL started; the passing Ubuntu 24.04 pilot did not test that case.

Please decide whether to keep the kernel-only Linux support claim and invest in a relocatable bundled or static user-space runtime, or amend the specification to state a supported user-space ABI floor and its test environments. Until the decision is implemented and tested, Linux archives must not be advertised as universal across distributions.

A 2026-10-16 probe confirmed the gap: the local PostgreSQL 18.6 x86-64 archive (`SHA-256 7a41e9d4287c49f5a9885ed53667add5b4a0ea52dc8e157d28f4a7c06ad8d34c`) failed to run `postgres --version` in an Ubuntu 20.04 Docker container with glibc 2.31. The loader reported missing `GLIBC_2.33` through `GLIBC_2.35` symbols in PostgreSQL and bundled libraries. The container shares the host kernel, so this does not test the kernel 5.15 endpoint.

Answer: I would ideally like to keep the kernel only Linux support claim if practical. Do experiments to work out how we can do this. Clearly, we cannot depend on a host libc. We will need to bundle or statically link a libc. This is not my area of expertise, so don't take this as a mandate. But experiment around this. If you successfully create a solution that meets the project's quality standard, then you can implement it and remove this item from the queue. Otherwise, update it with your findings indicating that you believe that this is not possible without unacceptable hacks.

Research direction: A bundled dynamic glibc and relocation-aware launcher is the current pilot approach. Static libc builds conflict with PostgreSQL's loadable extension model. Host NSS modules and locale data remain specific risks. See [glibc's runtime-linker guidance](https://sourceware.org/glibc/manual/2.40/html_node/Dynamic-Linker-Hardening.html) and [musl's static `dlopen` limitation](https://www.openwall.com/lists/musl/2014/08/27/16).

A disposable 2026-10-16 x86-64 probe copied the Ubuntu 22.04 `libc6` loader and libraries beside PostgreSQL 18.6 and used same-directory launchers with the loader's `--argv0` option. After relocation, the tools initialized and stopped a server, resolved `localhost`, loaded `hstore`, used a bundled ICU collation and ran `pg_dumpall` on both Ubuntu 20.04 and Alpine 3.22 containers. Alpine has no glibc, so the tested path did not require a host glibc. The reproducible Linux arm64 pilot build now uses this design and its final archive passed the same two containers plus the fuller Ubuntu 24.04 relocation suite locally. Its glibc mapping records the exact Ubuntu source-package version, source links, copyright and referenced licence texts. Alpine `initdb` warned that no system locales were found; the `C` locale and ICU operations tested still passed. Native CI results, a kernel 5.15 endpoint, and broader runtime and locale checks remain before a universal Linux claim is justified.

## Address Standardizer US data redistribution

The [Address Standardizer project](https://github.com/postgis/address_standardizer) provides `address_standardizer` and `address_standardizer_data_us`. Its source says the latter includes city-name files derived from USPS data. The repository licence covers project code, but the reviewed upstream material does not establish redistribution rights for those data files. [USPS AIS resources](https://postalpro.usps.com/resources/address-quality/ais-viewer) refer to a separate data licence; its applicability to these particular files is unresolved.

The functional specification prohibits including a project when merely creating its extension and using its objects in schema DDL depends on data that cannot be redistributed. Please determine whether the US data in this extension may be freely redistributed in public archives, or provide a source that establishes the rights. Until then, do not advertise either SQL extension from this project. Other extension and PostgreSQL work can proceed.

Answer: With no specific licence given for the data, we can assume that the open source licence that applies to the code also applies to the data.

## Minimum OS endpoint testing on standard GitHub runners

The [testing specification](specs/testing.md) requires final archives to run on clean systems at the minimum and current OS versions for every supported architecture. [The OS policy](policies/os-support.md) currently selects macOS 11.0, Windows 10.0.10240.0 and Linux kernel 5.15 as intended minima; none has a direct job label in the [current standard GitHub-hosted runner matrix](https://docs.github.com/en/actions/reference/runners/github-hosted-runners). Its macOS 11 and Windows 10 hosts are absent, and the [Ubuntu 22.04 image](https://github.com/actions/runner-images/blob/main/images/ubuntu/Ubuntu2204-Readme.md) runs a newer kernel. Containers share the host kernel, so they cannot establish the Linux 5.15 endpoint. GitHub describes nested virtualization as [unsupported and experimental](https://docs.github.com/en/actions/concepts/runners/github-hosted-runners); a reliable guest test path has not been demonstrated.

Please decide whether to authorize a suitable endpoint test environment beyond standard GitHub-hosted runners, or revise the OS minima and test-environment requirements in the specifications and repository instructions. macOS 15 is a candidate minimum with direct x86-64 and arm64 runners. A newer Linux floor may align with direct runners after both kernel versions are checked. Windows x86-64 standard runners are Server editions, while the available Windows client runner is arm64 Windows 11, so raising the Windows floor alone does not resolve the client endpoint. Until the decision and endpoint tests, do not advertise these minima or treat a current-runner smoke test as endpoint evidence. Other policy and implementation work can proceed.

Answer: look into QEMU, or other solutions for running a linux distro of choice on Github Actions. If it is straightforward to set up, no unusually high maintenance burden compared to the other things we're doing in this repo, go ahead with it. Basic idea is:

GitHub Actions runner, current Linux
  └─ QEMU virtual machine
       └─ Ubuntu userspace + Linux 5.15
            └─ Our tools

Otherwise we'll make do with the runners we have, and document that support is intended to be Kernel 5.15 but could only be tested back to {version}

Current status: The manual QEMU TCG job in `.github/workflows/linux-qemu-515.yml` is a candidate Linux x86-64 endpoint test and has not run yet. The fallback to newer runners would leave the minimum-OS checks in [specs/testing.md](specs/testing.md) unmet; it cannot establish release eligibility without a human specification change. The other OS and architecture endpoints also remain to be tested.
