# Human review queue

## Address Standardizer 3.7.0 on Windows

The selected [standalone 3.7.0 source](https://github.com/postgis/address_standardizer/tree/v3.7.0) documents a PGXS build and tests PostgreSQL 14–19 on Linux, but has no Windows build instructions or CI target. A 2026-10-18 review of [PostGIS Windows build documentation](https://postgis.net/development/docs/environment/windows/) found MSYS2 and Winnie procedures for PostGIS itself, with no documented application to standalone Address Standardizer 3.7.0. Our [native Windows probe](https://github.com/BernieSumption/pg_binaries/actions/runs/39062327837) built unmodified PCRE2 and compiled eight of 13 Address Standardizer C files with `clang-cl` against the PostgreSQL 18.6 pilot. It then failed because `pagc_tools.c` calls POSIX `getcwd`, which is undeclared under that Windows toolchain. MSVC also rejected GNU-style macro syntax and an exported-function declaration earlier in the source. A source edit or build-time API substitution could work around these errors, but the functional specification prohibits porting upstream packages.

Decision needed: Should we treat Windows as unsupported by this upstream release and remove both SQL names from the intended Windows support matrix, or is there an upstream-supported, unmodified-source Windows build method we should try? If Windows support is required despite the source issues, that would need an explicit specification change. Until resolved, retain the declared Windows targets as unverified and continue Linux/macOS work.

## Scope of the upstream-only source rule for packaged dependencies

The [functional specification](specs/functional.md#never-patch-or-modify-extensions-or-dependencies) requires straightforward upstream builds without modifying dependencies. The macOS 11 dependency-floor probe built suitable Mach-O targets with vcpkg, but its port recipes applied source patches to libxml2, LZ4 and OpenSSL. The Windows pilot also obtains PostgreSQL dependencies through vcpkg. At its newly pinned registry revision, the [libxml2](https://github.com/microsoft/vcpkg/blob/9e593bb18ea69cc5095e012465dcd675a822ed0d/ports/libxml2/portfile.cmake), [OpenSSL](https://github.com/microsoft/vcpkg/blob/9e593bb18ea69cc5095e012465dcd675a822ed0d/ports/openssl/portfile.cmake) and [Zstandard](https://github.com/microsoft/vcpkg/blob/9e593bb18ea69cc5095e012465dcd675a822ed0d/ports/zstd/portfile.cmake) recipes each list source patches; verify the resulting Windows archive before attributing any particular DLL to those recipes. Linux archives copy runtime libraries from Ubuntu packages. [Exact-source review](support/evidence/linux-redistribution-audit-2026-10-17.md) confirms that the selected Ubuntu packaging applies source changes to ICU, liblzma, libxml2 and libxslt. Existing Linux packaging also changes ELF RPATHs after compilation, and macOS packaging rewrites Mach-O load paths for relocation.

Decision needed: Does the prohibition include source patches applied by a standard package manager or distribution before we receive its packages, and does it include post-build changes to binary load paths needed for relocation? Pending an answer, treat patched-source dependencies as ineligible for release evidence. Continue independent implementation and tests; do not claim the current platform archives meet the upstream-only rule.

## seahash 4.1.0 redistribution notice

The selected `pg_jsonschema` release depends on `seahash` 4.1.0. Its [published manifest](https://docs.rs/crate/seahash/4.1.0/source/Cargo.toml.orig) declares MIT and names two authors, but neither the [published crate](https://docs.rs/crate/seahash/4.1.0/source/) nor its exact [source revision](https://gitlab.redox-os.org/redox-os/seahash/-/tree/94b632aeac099031c373599313d5b5f0acbbaec0) supplies a licence text or copyright notice. [Retained source research](support/evidence/pg-jsonschema-crate-licenses-2026-10-18/README.md) recovered exact upstream notices for the other five missing Rust crate texts. The MIT form requires retention of its copyright and permission notices, but the authors field does not state a copyright holder or year.

Decision needed: May the project use the standard MIT text with a notice explicitly attributed to the named authors despite the missing upstream notice, and if so what attribution should it print? Otherwise, keep `pg_jsonschema` redistribution review pending until upstream supplies a notice. Its builds and runtime tests may continue, but do not mark their archives eligible for publication.

## Backlog ideas

From Bernie: Adding this here so that we don't forget it. Don't start work on this yet. I'd like to discuss the viability of these and specify them properly before we go ahead. If indeed we decide to go ahead at all.

1. Size review. Look for ways to reduce binary size before building out the backlog of many versions. Potential options include compiler flags like -Os, reviewing the enabled build options for any that provide does proportionately small value in return for their increase in binary size, different compression algorithms and so forth. As a first step in this, some analysis about of the built archive to get a picture of what the greatest contributors are to size might be helpful.

2. Adversarial correctness review. Have an Astra agent review the implementation and tests to identify both specific and systematic potential issues.

3. Manual post-release bug hunting. Discuss and specify an occasional, manually initiated process that downloads and exercises released assets in environments outside routine GitHub-runner coverage. Examples include different operating systems and distributions (including older Ubuntu, outside the routine Alpine verification environment), older OS versions and Linux kernels, different distros, Windows without the Visual C++ redistributable installed, and macOS without development tools. These investigations seek production bugs and inform fixes and useful regression tests; they are not an automatic CI job or a prerequisite for each release. Decide the process before implementing it.
