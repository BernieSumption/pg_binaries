# Human review queue

## Temporary production release scope

The [functional specification](specs/functional.md) currently requires every qualifying stable PostgreSQL 15+ release on Linux, macOS and Windows, plus the extension versions selected under its compatibility rule. A production release containing only a subset would conflict with that requirement even if `support.json` and coverage reporting kept the missing targets visible. The current declaration has 105 PostgreSQL platform/version targets and 2,291 extension SQL targets. A latest-version release would reduce historical build and compatibility work but would not itself resolve clean-machine portability, redistribution obligations or post-publication retrieval checks.

Proposed first scope, if a staged production rollout is desired: PostgreSQL 18.6 and pgvector 0.8.7 on Linux x86-64 and arm64, retaining all bundled PostgreSQL extensions. These targets have the most developed publication-profile checks. PostGIS 3.6.4 and TIGER Geocoder 2025.2 are promising next additions on the same two platforms, but their larger dependency and redistribution review should not delay the smaller first set. PostgreSQL 17.11 is the next candidate core version. This proposal is a sequence for review, not an exception under the present specification; none of these assets is ready to advertise until the applicable Linux portability and redistribution requirements pass.

Decision needed: Keep the present full-support requirement before the first production release, or amend the specification to permit an explicit initial release subset while retaining the full intended-support declaration and visible unmet coverage? If allowing a subset, decide whether the proposed Linux PostgreSQL 18.6 plus pgvector scope is appropriate, and state which guarantees apply to it. Until the specification changes, the full-support requirement remains in force.

## online_advisor inclusion

[online_advisor](https://github.com/knizhnik/online_advisor) observes query execution and proposes index and extended-statistics DDL. [Neon offers it on PostgreSQL 17](https://neon.com/blog/easier-postgres-fine-tuning-with-online_advisor), which is a positive factor under the extension selection specification. Its [upstream repository](https://github.com/knizhnik/online_advisor) had 19 stars and one stable 1.0 release in October 2026; broad adoption is not established. PostgreSQL 14–16 require preloading the library before use, and its executor-hook integration adds version-sensitive maintenance. Upstream does not document an OS and architecture support range. Neon describes PostgreSQL 14–17 support, while PostgreSQL 18 support has not been established from upstream documentation.

Decision needed: Include this project despite limited adoption evidence and the expected cross-platform verification cost, or exclude it until broader adoption or compatibility evidence appears? If included, start with the documented PostgreSQL range intersected with this project's supported releases; do not silently narrow the intended OS and architecture scope to Linux merely because it is the first feasible pilot. Keep it outside `support.json` until the decision is made.

## Windows Visual C++ runtime redistribution

The Windows x86-64 pilot passes on Windows Server 2022, but its archive omits `VCRUNTIME140.dll` even though `postgres.exe` imports it. The runner has the Visual C++ runtime installed, so that result does not establish the [functional specification's](specs/functional.md) clean-machine installation guarantee. The archive must not be advertised as self-contained yet.

Answer: This question is phrased as a request for licencing permission, but there seems to be an unresolved technical issue behind it. First of all, determine what the preferred technical solution would be. Would we prefer to statically link or to bundle? If we bundle the Visual C++ redistributable, it is a package that needs to be installed, or a DLL that can ship in the folder and run locally? An installation is not acceptable, a DLL is. Establish the clear recommended technical solution, and then if this is blocked on a licence uncertainty, come back to me with that question By updating this item in the queue. If the preferred technical solution does not have a licence uncertainty, and feel free to research this yourself, then just implement it, and then you can remove this item from the queue.

Technical conclusion, 2026-10-17: Bundle the required Visual C++ DLLs beside the PostgreSQL executables. [Microsoft documents application-local deployment](https://learn.microsoft.com/en-us/cpp/windows/choosing-a-deployment-method?view=msvc-170); it needs no installer or administrator rights. Static `/MT` linking would require a consistent runtime mode across PostgreSQL and its dependencies and is more disruptive. The build should derive the non-UCRT DLL import closure across all packaged PE files, copy only unmodified files from the selected toolset's [redistributable list](https://learn.microsoft.com/en-us/visualstudio/releases/2026/redistribution), and verify that imports resolve from the archive after relocation. Windows 10 and later supply the [Universal CRT](https://learn.microsoft.com/en-us/cpp/windows/universal-crt-deployment?view=msvc-170). Both current CI jobs use Windows Server 2022 runners with the runtime installed, so their passing checks cannot establish clean-machine operation; the final archive still needs a Windows 10+ x86-64 test host without Visual Studio or the Visual C++ runtime.

Decision needed: Which Visual Studio licence covers the project's build and release operator, including use of the toolset on the GitHub-hosted runner, and does it authorize redistribution of these individual DLLs? [Microsoft limits redistribution to licensed Visual Studio users](https://learn.microsoft.com/en-us/cpp/windows/redistributing-visual-cpp-files?view=msvc-170). Its [Community guidance](https://www.microsoft.com/licensing/guidance/Visual-Studio) allows use for qualifying open-source projects but does not identify this project's licensed operator. Once entitlement is established, implement and verify app-local bundling; no installation prerequisite is acceptable.

## Linux user-space compatibility floor

The [functional specification](specs/functional.md) requires one Linux archive per architecture to work across supported machines without non-universal external dependencies. The [OS policy](policies/os-support.md) states only a kernel 5.15 minimum. A kernel version does not identify the C library or dynamic loader. The earlier Linux pilot used Ubuntu 22.04 and left glibc and the ELF loader outside the archive. A clean machine with kernel 5.15 and an older or different libc could fail before PostgreSQL started; the passing Ubuntu 24.04 pilot did not test that case.

Please decide whether to keep the kernel-only Linux support claim and invest in a relocatable bundled or static user-space runtime, or amend the specification to state a supported user-space ABI floor and its test environments. Until the decision is implemented and tested, Linux archives must not be advertised as universal across distributions.

A 2026-10-16 probe confirmed the gap: the local PostgreSQL 18.6 x86-64 archive (`SHA-256 7a41e9d4287c49f5a9885ed53667add5b4a0ea52dc8e157d28f4a7c06ad8d34c`) failed to run `postgres --version` in an Ubuntu 20.04 Docker container with glibc 2.31. The loader reported missing `GLIBC_2.33` through `GLIBC_2.35` symbols in PostgreSQL and bundled libraries. The container shares the host kernel, so this does not test the kernel 5.15 endpoint.

Answer: I would ideally like to keep the kernel only Linux support claim if practical. Do experiments to work out how we can do this. Clearly, we cannot depend on a host libc. We will need to bundle or statically link a libc. This is not my area of expertise, so don't take this as a mandate. But experiment around this. If you successfully create a solution that meets the project's quality standard, then you can implement it and remove this item from the queue. Otherwise, update it with your findings indicating that you believe that this is not possible without unacceptable hacks.

Research direction: A bundled dynamic glibc and relocation-aware launcher is the current pilot approach. Static libc builds conflict with PostgreSQL's loadable extension model. Host NSS modules and locale data remain specific risks. See [glibc's runtime-linker guidance](https://sourceware.org/glibc/manual/2.40/html_node/Dynamic-Linker-Hardening.html) and [musl's static `dlopen` limitation](https://www.openwall.com/lists/musl/2014/08/27/16).

A 2026-10-17 disposable-container probe of the x86-64 PostgreSQL 18.6 archive (`SHA-256 73fbb63353eb5c88ea03174781639e11d787b581debd8f1b48d323b09f7ce42b`) found that `initdb --encoding=UTF8 --locale=C.UTF-8` succeeded as an ordinary user on Ubuntu 20.04 but failed with `invalid locale name` on Alpine 3.22. `en_US.UTF-8` failed on the Ubuntu 20.04 container without generated host locale data. The archive includes no locale data. The existing portable verifier uses `--locale=C` and checks ICU collation operations, so it does not establish support for named libc locales. Decide during the broader Linux portability review whether common named libc locales must be bundled and tested, or whether the universal interface is limited to C and ICU collations; an archive must not imply that arbitrary host libc locales are portable.

A disposable 2026-10-16 x86-64 probe copied the Ubuntu 22.04 `libc6` loader and libraries beside PostgreSQL 18.6 and used same-directory launchers with the loader's `--argv0` option. After relocation, the tools initialized and stopped a server, resolved `localhost`, loaded `hstore`, used a bundled ICU collation and ran `pg_dumpall` on both Ubuntu 20.04 and Alpine 3.22 containers. Alpine has no glibc, so the tested path did not require a host glibc. The reproducible Linux arm64 pilot build passed the same two containers plus the fuller Ubuntu 24.04 relocation suite locally. Native Linux x86-64 and arm64 CI passed these tests for the dynamic glibc pilot on 2026-10-16. The subsequent arm64 static launcher archive passed the full local relocation suite and started in a `scratch` container with no host shell or C library. The archive maps the bundled glibc and static musl launcher to exact Ubuntu source-package versions, source archives and copyright files. Alpine `initdb` warned that no system locales were found; the `C` locale and ICU operations tested still passed. The static launcher later passed native CI on [x86-64](https://github.com/BernieSumption/pg_binaries/actions/runs/38980539473) and [arm64](https://github.com/BernieSumption/pg_binaries/actions/runs/38980539490), including the Linux 5.15 QEMU endpoint for the same archive bytes on each architecture. Broader runtime and locale cases remain open before a universal Linux claim.

## Address Standardizer US data redistribution

The [Address Standardizer project](https://github.com/postgis/address_standardizer) provides `address_standardizer` and `address_standardizer_data_us`. Its source says the latter includes city-name files derived from USPS data. The repository licence covers project code, but the reviewed upstream material does not establish redistribution rights for those data files. [USPS AIS resources](https://postalpro.usps.com/resources/address-quality/ais-viewer) refer to a separate data licence; its applicability to these particular files is unresolved.

The functional specification prohibits including a project when merely creating its extension and using its objects in schema DDL depends on data that cannot be redistributed. Please determine whether the US data in this extension may be freely redistributed in public archives, or provide a source that establishes the rights. Until then, do not advertise either SQL extension from this project. Other extension and PostgreSQL work can proceed.

Answer: With no specific licence given for the data, we can assume that the open source licence that applies to the code also applies to the data.

Further finding: The [PostGIS 3.6 build rules](https://github.com/postgis/postgis/blob/stable-3.6/extensions/address_standardizer/Makefile.in) generate `address_standardizer_data_us` SQL from the US gazetteer, lexicon and rules files; the [control file](https://github.com/postgis/postgis/blob/stable-3.6/extensions/address_standardizer/address_standardizer_data_us.control.in) declares no city-list dependency. The same build compiles `parseaddress-stcities.h` into the `address_standardizer` library. The [upstream README](https://github.com/postgis/postgis/blob/stable-3.6/extensions/address_standardizer/README.address_standardizer) says the source city list was extracted from USPS. Inference: a binary archive containing `address_standardizer` likely redistributes derived USPS city data even when it omits the source text file. No source reviewed so far identifies the exact USPS product, its terms, or an upstream grant covering that extract. The user's assumption resolves the unlabelled SQL data files but does not establish whether upstream can license the separate USPS-derived material. Keep both SQL extensions outside advertised support under the project's project-level decision rule until this provenance is resolved or the derived city list is excluded from the build. Decision needed: Does your assumption also cover this identified USPS-derived city list, or should these extensions remain excluded pending a rights statement or an independently licensed replacement?

## Windows UUID-OSSP dependency

The [PostgreSQL option policy](policies/postgres-options.md) includes `uuid-ossp` because its functions can occur in schema defaults, but the Windows pilot does not build it. PostgreSQL 18's [Windows build notes](https://www.postgresql.org/docs/18/installation-platform-notes.html) require OSSP UUID for this extension. PostgreSQL's [extension documentation](https://www.postgresql.org/docs/18/uuid-ossp.html) says OSSP is not well maintained and increasingly hard to port. The only native Windows source candidate found is a [SourceForge beta port](https://sourceforge.net/projects/osspuuidwin32/) based on OSSP 1.6.2, with a 2012 source archive and no upstream checksum or maintained repository. Using it for public archives would require porting its old Visual Studio project, pinning and preserving the source, and establishing its ABI and security maintenance. PostgreSQL core already supplies UUID version 4 and 7 generators, but not every `uuid-ossp` function.

Proposed decision: exclude `uuid-ossp` from Windows if the portability and maintenance costs outweigh support for its additional UUID functions; keep it on Linux and macOS. The functional specification allows excluding an option that conflicts with portability, but also calls for including options used by plausible schemas. Both considerations are substantial here, so this choice needs human review. Until resolved, the Windows archive must not claim full PostgreSQL option coverage. A bounded buildability spike with the beta port is possible if the additional functions are important enough to justify maintaining it.
