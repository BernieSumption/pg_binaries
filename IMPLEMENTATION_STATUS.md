### Parallels recommendation

Research checked on 30 October 2026. Trial Parallels Pro for Windows 11 ARM before purchasing it. Its CLI is a plausible common control interface for Windows, Linux and macOS ARM guests. Pro or Business/Enterprise is required for the documented automation interface; the trial includes Pro features. The published US Pro list price is $119.99/year, with Windows licensed separately. No Parallels software was downloaded or installed. [CLI guide](https://docs.parallels.com/landing/parallels-desktop-developers-guide/command-line-interface-utility), [14-day trial](https://www.parallels.com/products/desktop/trial/), [published pricing](https://www.parallels.com/blogs/parallels-desktop-vs-windows-laptop-cost/), [Windows licensing](https://kb.parallels.com/en/9003).

Windows ARM can use native ARM-hosted MSVC to produce x64 binaries and Windows's application translation to execute them. This looks more promising than emulating an entire x86 Windows VM. Whether PostgreSQL's selected dependencies and extensions work with that toolchain remains untested. Parallels cannot replace native Intel Mac validation on this host. [MSVC host/target support](https://learn.microsoft.com/en-us/visualstudio/install/visual-studio-on-arm-devices?view=visualstudio), [Windows application emulation](https://learn.microsoft.com/en-us/windows/arm/apps-on-arm-x86-emulation).

Parallels also supports Rosetta for x86_64 binaries and containers inside an ARM Linux VM. This is a separate, more promising Linux route than its full x86 guest emulator, and resembles our current Docker translation setup. The trial should compare direct Linux VM builds with running the existing container loop inside that VM. Keeping Docker Engine there could preserve the tested container environments while replacing Docker Desktop's separate VM; its extra layer needs to earn that benefit in the experiment. [Linux Rosetta support and limitations](https://kb.parallels.com/en/129871).

Full x86 guest emulation remains worth a short comparison experiment, rather than an assumed percentage slowdown. Parallels documents an early preview limited to one vCPU and 8 GB guest RAM, substantial host overhead and unstable Linux Tools support. These restrictions make it a poor first choice for dependency-heavy builds, but no PostgreSQL build benchmark was performed. macOS ARM guests have a separate limit of two running VMs, restricted configuration and documented network issues. [x86 guest limitations](https://kb.parallels.com/en/130217), [macOS ARM limitations](https://kb.parallels.com/en/128867).

The documented Mac guest floor is macOS 12, so this cannot provide an actual macOS 11 minimum-version test. Parallels also cautions that creating a guest with a different OS version may require creating it on another Mac and transferring it. These restrictions matter for compatibility testing even if current-version local builds work. [Mac guest installation and version restrictions](https://kb.parallels.com/en/125561).

`prlctl` documents lifecycle, cloning, snapshots, resource configuration and guest operations. Guest execution relies on Parallels Tools; exact exit-status propagation, durable logs and dependable transfer need a trial. SSH/SCP provides a fallback where guest integration differs. The common interface could simplify local tooling, but does not make all guest capabilities identical. No additional SDK appears necessary for the proposed loop. [VM command reference](https://docs.parallels.com/landing/parallels-desktop-developers-guide/command-line-interface-utility/manage-virtual-machines-from-cli).

The host has an M5 Max, 18 logical CPUs, 128 GiB RAM, macOS 26.6.2 and approximately 1.1 TiB free on its data volume. These are measured host resources, not Parallels memory-use measurements. A starting experiment budget is 8 vCPUs/16 GiB for a Windows build VM and 4 vCPUs/8 GiB for a clean verifier, with the verifier stopped when idle. Begin with two active guests and retain at least 48 GiB for the host and other work. Smaller allocations are worth testing; useful concurrency depends on measured CPU throughput, memory pressure and swap, while the Mac guest limit remains two regardless of available RAM.

After installation, the bounded experiment is:

1. Prepare a licensed Windows ARM base and ARM-hosted MSVC. Automate clone/start/stop/delete, a failing command's exit status, stdout/stderr capture, transfer with matching hashes, and recovery after interruption.
2. Compile and execute an x64 sample, then PostgreSQL and one small extension. If that succeeds, try a dependency-heavy package and final-archive verification in a clean clone. Record Windows portability gaps separately from VM failures.
3. Compare three repeated local iterations with GitHub feedback, including queue and transfer time. Test Windows x64 application translation and Linux Rosetta first, then give full x86 guest emulation a bounded boot/compile/run sample before deciding whether its slower execution is still useful.
4. Test two concurrent builds, idle memory, clone/disk growth and host responsiveness. Trial equivalent Linux and Mac build/clean loops before consolidating those platforms. Native ARM turnaround should stay within 20% of the existing loop unless simpler operation justifies the difference; this is a proposed acceptance threshold, not a measured result.

Retain Docker and Lume during the trial because their loops already work. Retain either long-term only where a measured Parallels limitation justifies the additional tool: failure to automate, verify the same packages or sustain useful resource usage. A separate clean verifier can be a Parallels clone; it does not inherently require another VM product. GitHub remains necessary for native Intel Mac evidence and useful when local emulation loses the turnaround comparison. Final environment selection and concurrency limits remain human decisions in the review queue.
